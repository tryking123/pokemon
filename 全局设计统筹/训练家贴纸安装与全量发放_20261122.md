## 接口与刻印规则

| 请求 | 业务与约束 |
| --- | --- |
| C2528 `suit_equip` | 提交装备槽 `pos`、贴纸模板 `material`、原概率 `probability`；本地业务校验已穿戴槽、角色等级、未锁定贴纸数量、同槽不重复、套装上限及金币。扣一张贴纸、支付金币、开启新位或覆盖原位和写入回执位于同一事务。 |

每个装备槽最多三枚刻印；使用既有 `engrave` 配置及 `sets` 档位，不改概率、金币和分解数。套装属性按实际穿戴位的同套件数叠加第 1 档到已达档。恢复入口不自动穿戴训练家装备，不退回已刻印贴纸，不重置刻印。

## 道具发放与领取存档约束

1. 道具发放新增“贴纸”分类。数据来自全量 `suitname_proto` 并与 `trainer-runes.json.stickers` 逐 ID 对齐；不用品质筛掉原模板。展示名称、贴纸 ID、品质和刻印等级；仍可搜索并输入正整数数量。
2. 沿个人信息→道具发放→邮件→领取流程，目录只接受 `type=12` 和有效贴纸 ID。发送身份及本角色归属校验保留，同一稳定 `requestId` 只创建同一邮件。发放不自动执行刻印，也不受当前刻印等级限制；等级在安装时校验。
3. 原 `ghelper.parse_reward` 原生解析 `suit_bag` 为 `ITEM_TYPE.SUIT`；其底包函数原型包含 `suit_bag`、`SUIT`、`id`、`n`，无需包装普通 `items` 或借用精灵装备字段。附件应保留 `suit_bag` 语义并用贴纸 ID 显示原图标、名称。
4. 领取向 `local_trainer_sticker(role_id, sticker_id, amount, locked)` 入账，不写普通物品表。相同模板占一格并累加；新模板必须有普通背包容量；数量不得越过整数上限。容量或堆叠不足，实际接收量之外的附件保留邮件，写入实际 `claimed_quantity`。
5. 贴纸增加、附件已领数量、邮件状态和领取回执同事务提交；同回执重放、重复点击或重登均不能重复增加。多附件允许保留未收数量，不能先将整封邮件标记领取后漏发贴纸。
6. 提交后先发送背包和刻印的绝对快照，再返回领取成功，避免原 `gbag_model` / `gsuit_model` 缓存残留。既有 `local_trainer_equipped`、`local_trainer_engraving`、`local_trainer_rune_shop` 与历史贴纸/锁定状态全部保留；不新增破坏性迁移。

## 验收与生效条件

- 静态检查：214 个目录 ID 与运行资源逐项相符；`type=12` 不与普通物品、精灵装备 ID 混用；共用 UI 资源恢复 Mark、SuitList，两个 ABI 原 Lua 保持兼容；原 `parse_reward` 能把附件显示为贴纸。
- 业务检查：首尾 ID 1、214及同名不同 ID 发放；同发送回执幂等；领取重复回执幂等；满仓新模板留邮、已有模板可继续堆叠；腾格后领尽；无效 ID 和非正数拒绝；混合附件已领取量正确。
- 安装检查：穿戴训练家装备后可从详情进入，选择实际持有的贴纸、显示费用和原概率；等级不足、锁定、同槽重复和金币不足按原规则拒绝；成功只扣一次，刻印与属性变更后刷新列表。
- APK 与设备：App 独立构建不读取服务端目录；包内 UI 资源补丁、双 ABI 兼容、运行资源、签名和 16 KB 对齐检查通过后才作为候选版本。设备在断外网、无 PC 服务和无 ADB 反向转发条件验证邮件显示→领取→安装→重启存档。上述为验收要求，不能把底包取证或代码完成写成实机通过。
