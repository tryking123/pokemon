## 共用本地流程

### admin 存档的归属与身份转换

2026-11-22 起，存档以本地登录名 `admin` 定位账号，涵盖该账号在各区的所有角色。账号和角色的数据库主键可以随存档迁移改变。各区角色、资产、订单、已领奖回执及战斗进度随该账号迁移。登录会话留在原设备。

| 数据 | 导出与导入口径 |
| --- | --- |
| 账号及个人记录 | 按 `local_account.username` 确认账号，再由 `local_game_role.account_id` 得到角色集合。按表的 `role_id` 或 `account_id` 提取业务记录。没有归属的行排除出导出文件。 |
| 间接记录 | 系统邮件附件按邮件主键，豪华礼包订单按支付订单主键，训练家装备属性按探险装备实例主键确定归属。 |
| 世界首领 | 按区、模式和周次携带 admin 各角色的伤害榜项；导入时合并对应榜项，沿用目标设备的场次、血量与其他玩家排名数据。 |
| 洞穴层人数 | 导入时根据新旧 admin 的逐角色通关记录，对目标设备对应层的累计人数先扣除旧贡献，再加上新贡献。 |
| 区服公共数据 | 活动日历和道馆站点锁使用目标设备的记录。新业务表缺少可识别的归属字段时，停止导入导出并提示表名。 |

选择重新生成 ID 时，为账号分配正整数 ID，并为每一名角色分配 UUID。同步更新个人表外键、含角色 ID 的复合键及 JSON 状态中的角色引用和榜单索引。接受旧档时保留独立订单号和邮件号，通过外键校验确认关联。导入在目标库单一事务内替换旧 admin 记录；如与其他账号的唯一键冲突，回滚整个导入。

验收覆盖已有 195 张业务表的旧档副本，加入独立账号和同一期世界首领榜，并在同一洞穴层建立两名角色的通关记录。核对导出归属、ID 转换、其他玩家榜项、全服血量、层人数及 SQLite 外键检查。当前新增的初始精灵领取表通过 `role_id` 归入角色。

### 玩法共用规则

| 环节 | 设计口径 |
| --- | --- |
| 角色与时间 | 从已验证的本地会话定位账号与角色。以北京时间 00:00:00 自然日、活动轮次或已批准档期生成业务周期键。旧档先保留已领、已通关及装备记录。跨日、跨周和跨轮只切换对应业务的记录范围。 |
| 进入页面 | 直接从本地表取得可用入口、进度、货架、日期和已领状态。必要的原协议应答从同一份数据生成。未查明原条件或者没有可验证配置的分支保持隐藏。 |
| 提交操作 | 只接收当前玩家选择的目标、选项或动作。业务从本地快照核验拥有关系、资格和费用，原子写入实例、消耗、结果、发奖记录。配置保存版本，已经开始的战斗、模拟订单和抽奖轮次按冻结版本完成。 |
| 结算及重试 | 每类操作采用真实业务唯一键，优先用订单号、活动期加档位、尝试 ID 加动作序号、日期加奖励编号或开箱实例。写入完成才返回成功，重连重读已存回执。无实例号的原协议由本地业务把请求映射到当前有效批次或场次。 |
| 战斗 | 显示服务从本地战斗快照取数。尝试内保存冻结阵容、技能、回合、种子、天气、有效伤害、结束状态及配置版本。C3001 用动作推进战斗，伤害、胜负和收益由本地战斗规则计算。C3002 只结束该未结算尝试。胜利、失败、退出和断线分别结算一次，结算后禁止续写回合。 |
| 阵容 | 按 NPC 配置的 `modes[].id` 选择模式，从该模式的 `pool` 解析 `rosters[].id`，并在尝试内冻结 `configVersion`。先通过模式 `gate`，属性需按原模板或已验收的本地战斗适配解析。匹配列表及战斗的 `isnpc` 按原结构填写。本机赛季的 `league_player` 没有该字段，用 `npc:` 前缀和可见名称区分。NPC 只进入明确允许的训练或本机赛事榜。 |
| 配置缺口 | 优先查同版本随包数据、取证记录和 App 当前资源。没有可验证来源的字段写明缺口和对应入口，按数值或阵容产物决定候选值及上线条件。数值交接包括币种、单位、奖励 ID、公式、上限、概率、重置时点和计算校验。 |

## 已明确开放的单机玩法

### 本机个人公会与首领

C50–C69、C1401–C1403、C5070–C5072 共用本地公会和成员记录。角色可创建个人公会，创建事务同时建立唯一有效公会关系和该角色的会长权限。查询、搜索、成员列表、简介及日志均读本地公会。新旧入口映射到同一公会 ID。

- 申请、审核、移除和关系变更仅针对数据库内有效成员或申请。当前个人公会没有其他成员，展示空的成员申请列表和对应不可用状态。公告、简介和自动审核可面向本地会长设置。离会确认后结束当前成员关系，历史捐献与结算仍绑定原公会。
- C65 按已核定的捐献档从本地钱包扣费，将个人贡献、公会进度及回执一次提交。成员可购买的商品读取本地真实贡献余额。
- C5071 校验会长、资格及已开场次，再冻结指定档期和首领。C5072 查公会档期与阶段。C5070 从有效场次选择阶段开启本地尝试。战斗伤害、回合限制和奖励资格从实际战斗结果读取。相同场次的通关和领奖分别去重。
- C66、C68–C69 查询对应次数、强盗首领与奖品预览。C127/C128 另有已批准的独立单人挑战，独立保存怪物出现、次数、战斗及奖励，建立个人公会和完成独立挑战之间没有资格依赖。

验收覆盖重复建会、无资格者修改、公会和独立强盗次数互不影响、同场首领奖只发一次、旧存档重启后日志连续。

### 三种 NPC 训练与单机赛季

| 原接口 | 本地流程 | 关键验收 |
| --- | --- | --- |
| C100–C103、C112 | 单人竞技读本机段位、C101 保存的单人阵容、有效批次和次数。C103 生成可复现的新匹配批次，C102 按当前 `pkrank` 定位 NPC 并冻结一场战斗。C112 购买该模式次数。 | 阵容位置及实例归属正确，旧批次目标不可再次开战，购买次数只进单人模式。 |
| C104–C106、C110、C113 | 竞技场读本地挑战阵容与匹配批次，按当前排名索引和 `teamid` 解析对手与出战队。刷新只替换尚未锁入战斗的那批对手。C110 购买次数，C113 按自然周及已达档领奖。 | 排名来自本机战绩，次数与单人竞技、精灵王隔离，周榜获奖和回执在周界线正确切换。 |
| C107–C109、C111 | 精灵王按 `type` 与 `positionid` 维护随包允许的多个分路阵容，C109 按分路与 `pos` 建立尝试。榜单、额度及购买按该模式配置。 | 核对同一精灵能否在多分路占用，原阵形槽位取已有配置。分路有效战绩和购买次数重启可查。 |
| C234–C245、C249–C250 | 独立单机赛季采用「报名 → 分组 → 对局 → 结算 → 可查回放」。报名冻结本机阵容与本期 NPC 名单，赛程只读取本地时间和关卡。已发生对局保存双方阵容、种子和结果，榜单、分组、点赞和录像逐条从已结算记录读取。 | 未报名不进入比赛，已进行赛季不受临时阵容和热更影响。相同种子和快照得到一致结果，重启可查同一场回放。 |

C234 报名后，按本机角色 1 席、NPC 7 席组成本机赛季。分为两组，每组四席单循环。组内按胜场排序，同分优先比较相互胜负，循环同分时比较有效击倒数之差及稳定席位编号。各组前二进交叉半决赛，决赛确定冠亚军。半决赛负者和未进淘汰赛的席位按已有成绩分别顺位。每期保存分组种子、席位、对局序号和结算结果。

已报名席位使用冻结阵容。进入页面时，由本地业务补做当前时刻之前已到期的对局和后续结算，每场按已保存的种子、阵容及规则生成一次结果。离线时长不改变赛程或随机序列。未报名的角色无本机参赛记录，也不会被补入已开始赛季。C249/C250 只读取有完整对局结果的录像。

按当前七日数值配置，第 1 日报名，第 2 至 4 日每天进行一轮组内对局，第 5 日进行半决赛，第 6 日进行决赛，第 7 日结算排名、竞猜及奖励。活动调档时整场赛程按报名时配置冻结。领奖时只计完整、有效的已结算场次。批次中未完成的有效投注按数值配置返还。

C244 的字符串入参按已登记房间和本地配置的竞猜档解析，只能使用指定的本地游戏内资产。每个房间关闭前登记一次投注，兑换、返还、奖励及对应账本都以比赛结算凭据去重。已经结束的房间只可查询。竞猜档、赛程和奖品使用数值产物。三种训练采用不同的 `modeId`、阵容、次数、匹配批次和奖励键。账号充值榜和个人公会席位不引用训练 NPC。

### 矿洞、道馆与每日副本

- C122–C126、C129 用本地矿位和配置、角色或 NPC 归属、起止时刻、可领游标。占矿时冻结适用产率与时长上限，重复领取沿游标累进。撤出按当次结算规则一次提交。C123 允许掠夺明确标注的矿洞 NPC。当前快照冻结矿位、目标与掠夺批次，获胜后只从该 NPC 产出预算结算，目标不可复用至下轮次。
- C268/C269 开放 NPC 道馆驻防与抢夺入口。C268 按护卫位置索引解析当前本地 NPC。真胜后保存该场占领与奖励流水，跌落或重置按配置切换归属。C269 只买抢夺次数。C180 阵容、C181 挑战和 C182 已接扫荡继续各自计数和结算。道馆归属和奖励来源使用独立记录，不能取用矿区或竞技对手的可领预算。
- C168/C169 的每日挑战与扫荡拥有独立额度和去重键。挑战开始时锁定关卡、难度和阵容，按配置扣挑战次数。扫荡要求已有该关有效通关，在同一事务扣扫荡次数、发奖和写回执。挑战不占扫荡次数，扫荡不占挑战次数。重试不影响另一额度。

### 两个单机世界首领及悬赏首领

C3651–C3653 与 C10033–C10036 分别保存档期、首领 ID、剩余血量、玩家挑战次数、买次数记录、首杀和档位领取。血量、排名和累积有效伤害从已结算场次读取。单局计分使用实际对首领造成的有效伤害，在该场允许范围内计入。HP 到零时只生成一条首次击杀。C3652、C10035 使用各自档位和已领记录，C10036 只修改第二种首领的当地次数。玩家活动时序与 NPC 阵容素材以本地时钟和配置为准。关闭跨服房间依赖后，原界面明确展示单机首领。

普通首领从冒险概览 9 寻路至主城 71002 的 (26,16) 格，S4、S801 原场景对象和 S12 离场共用同一实例 UID。原普通三组 300001–300003 按北京时间自然周轮换，每日 12:00–20:00 开一场。大师从概览 23 进入，沿用原 kfbossshow 六只及其本地成长属性，每日 12:00–13:00、21:00–22:00 各开一场。两种模式均为等级 1 开放。每个时段刷新同服所有角色共享的各阵位 HP，迟到的并发结算按剩余生命截断。按角色和模式独立记录北京日 1 次免费和 1 次确认后购买，每次 200 钻。撤退消耗已用机会，未结算场次不计伤害。

普通单场有效伤害率 2%、10%、30%，大师 2%、15%、40%，各场只给所达最高档。普通原奖励按钮在有达标记录时可寄取一场，也可取消后查看周榜奖。大师伤害档、两模式各自的本周首杀直接寄信。大师原累计挑战按钮保留 1/3/5/10 场规则。周一零点结清旧排行和普通待领奖，普通随机幸运奖按原幸运物品仅在本周有实伤的真实角色中无放回抽取，最多三名。实际发奖在角色下次进入时完成。期间重登、领取重放、两次确认同一购买均沿用实际收据。

独立旧 PC 存档在真实北京时间 14 时验证普通场从 471848 HP 实扣至 0，伤害与排名落盘，重启后同一笔 C3652 只寄一份。大师在该时间拒绝开战与购买。仅在隔离验收包固定时钟至 12:30 后，大师六只总血 3888 的战斗、原累计首档、两个模式各 200 钻购买、跨周补寄与周数据清零均通过。32/64 位原 LuaJIT 已核原地图弹窗周奖文案、大师付费确认和次数显示。本机正式包继续读取实际设备时间。

C10012–C10020 悬赏首领用独立首领轮换、选择和刷新、剩余次数、战绩与兑换账。累计积分与消费余额分别保存。资格结果、兑换和累计奖用不同回执，领取奖励不会回写战斗分数。

### 地下城（C293–C302）

C293–C302 已核九期原地下城均在每月1日至21日闯关，另有季末领取。1000层各引三组，有18000个原怪引用。阵位、原属性和技能已整理在 battle/dnf-rosters.json。每日挑战10次，自动扫荡原门槛VIP5。本地以 2026-11-16 为第一轮周一起点，九期循环保留当期奖表，周一至周六闯关、周日领取名次奖或百分比奖。当前服务已实现逐层回合、寻宝值、委托、抽奖、赛季排行及领奖。关卡快照、胜负、位次、扣费、重复提交、重新启动和换周均通过隔离存档验证。每次开场只占一次当日次数，委托时间用原分钟数，属性仅作用本场。APK 版本及设备范围以版本记录为准。

## 共用资产与领取约定

### 邮箱溢出及部分领取

入口覆盖 C282–C286 捕捉、狩猎、宝箱、活动奖、道馆和副本等容量受限的正向奖励。C1000 查询、C1001 领附件、C1004 阅读。C1003 给其他角色发邮件维持隐藏。当前 `InventoryService.claimMail` 以整封邮件领取为主，新的溢出流程需记录每条附件的未领数量，精灵、宠物和装备按唯一实例记录。

1. 业务保存一份确定的奖励清单和唯一回执。在角色资产事务里，将能容纳的部分按本地容量直接入账。其余对应原回执生成一封溢出邮件。稀有实例保留获得时确认的模板、随机结果和实例身份。
2. 领取时重新读取不同资产的当前可用容量。对于可堆叠项，按原附件顺序尽量入账。对于精灵、宠物、装备等实例，按可用槽逐个入账。附件原总量和已领取量分开记，剩余仍显示在同一封邮件中。
3. C1001 的应答只把已耗尽的邮件 ID 标为附件处理完。部分领取成功后页面直接查询 C1000，展示剩余数量。若旧界面会将已部分领取的邮件误清空，先完成本地列表刷新路径再开放该入口。无容量时当次库存、邮件明细和原领取数保持原值。

## 实现前核验与交付顺序

先串起本地业务层取数、角色会话、业务周期、战斗结算及附件部分领取。随后接已确认的离线角色权益、签到、积分、商城和单人玩法。各模块用已有本地资产、数值和阵容配置逐步解锁入口。以下检查属于研发取证。取证失败的入口保持对应的隐藏状态，已齐备的独立玩法可继续实施。

- 原接口字段与界面动作显式映射。优先核对 C2211 队伍、C246–C248 货架、C284 购买用途、C386 精灵实例确认、C400/C401 券箱语义、C5067 祈愿、C5090 触发点、C3551 图鉴动作和 C104xx 券种归属。
- 鉴权与乐观并发检查覆盖错误角色、过期批次、重复操作、运行中重启、正在进行的活动跨日和同一资产在多入口核销。
- 本地验收覆盖断网启动、旧档迁移、本地活动实际到达再领奖、模拟支付重复确认、三种训练模式切换、不展示明确关闭入口及所有部分领取场景。测试动作使用独立本机存档。
- 已标记的规则足以明确策划方向。活动 C172–C176 天数空位由数值统筹补齐。全称号属性口径采用持有生效、佩戴展示，兼容原条件，并在取证时核对配置。邮箱部分领取按同一封邮件保留未领附件。

## 417 条缺口的逐项路由

[未接入接口逐项索引](未接入接口逐项索引.json)记录清单基线中的 417 个不同编号。按编号查到原协议名后，用 groups 中的组名查 interface-design-routes.json，可取得玩法章节、处理方向和已登记的取证条件。C284 同时关联活动流程与自身入口，C10415、C10416 同时关联礼包与券档期。C131 的清单行单独说明 VIP 追加签到，免费补签由 C130 处理。

编队及技能验收沿用清单已有回环记录。C1502、C3018、C3023 涵盖下阵、状态与换位，C3012、C3017 涵盖装卸和战斗快照。C3043 在本渠道仅显示技能详情，无可触发升级的按钮。C3015、C3016 另属阵位养成，须先把原界面 type、number 对应到随包 array、team 的行及战斗槽位，再核对材料、满级余量和战斗属性。验收时应在相同角色状态下比对换位前后槽位与属性，并确认升级重放只扣一次。

### 阵法与副本队伍取证

C3015 的 number 是当前队伍页签，type 是点击的阵法按钮编号。原控制器用 type × 100 + lv 查 array_proto，尚无等级记录时用该类型一级。七类共 105 行的原表同时定义阵位加成和克制关系。主队选择已在服务端回环验证，C3016 升级及战斗加成仍待接入。

C2211 的 dungeon_navi_view 与 secretarea_navi_view 在所选队伍等于当前队伍时直接返回，在 teams 中没有候选队伍时提示，存在其他队伍才发送 tid。目前副本只有主队，需先接入第二支合法队伍的创建、参战和生命快照。

C3042 的原 Sproto 注释明确 start 和 final 为超速闯关起止关卡编号，adds 为奖励附件。需追踪 speed_ctrl、speed_model 的闯关资格和结算，不能将 C3039 两小时收益直接映射为关卡编号。

### 阵法培养与普通开战

原 formationup_view 从第 18 类背包只展示 number2 等于目标阵法类型的材料。item_proto 的 30001–30007 各对应一种阵法，number1 均为 50，variable_proto[1400].data1 为 100，同类型每份获得 100 经验。七种阵法各有 15 级，按 array_proto 的 levelup 扣除本级经验并保存余量，满级停止。原界面一键按钮按本级剩余所需选材，单次服务请求校验该上限及实际库存。

C3016 已支持扣材、升级、请求重放和重启恢复。普通副本的开战快照将当前类型 × 100 + 已存等级填入 formation_t.sid，原客户端 stage 的阵位属性与克制逻辑共用该编号读取 array_proto。普通竞技使用相同编号。当前回环验证覆盖升级到二级、余量、错误材料、超量、同会话重放与战斗锁。具体伤害差异仍待设备实测。

### C3003 批量放生的客户端依据（2026-11-19）

### 2026-11-22 · App 自有离线运行与 Unity 直接调用

本节按用户最新明确要求取代下节 v4 事务修正的运行架构：本次交付不编译、引用或启动 `服务端代码/`，App 内也不监听 HTTP、TCP 或其他回环端口。业务代码归属 `app端代码/local-patch/offline/src/com/pokemon/offline/`，业务资源归属同级 `offline/resources/`；Spring 同名兼容层改由 App 自有的 `com.pokemon.offline.platform` 组件承担。原 PC 工程及历史运行记录保留为来源，不能据此宣称新 App 已完成设备验收。

运行链为「原 Unity Lua 界面及 sproto 会话 → LuaJIT FFI → 同进程 `libpokemonoffline.so` JNI 桥 → `com.qk.local.OfflineBridge.exchange` → App 业务组件与私有 SQLite」。`offline-network.lua` 的 proxy 取代 C# `GetNetManager`，原请求和应答编码不改；请求帧以十六进制字符串传入 Java，提交后的响应与推送由 `poll` 取回交给原 `Network.OnMessage`。此处的连接仅指 App 内角色会话，不创建套接字。JNI 通过标准 UTF-8 字节数组转换 Java 字符串，不把 Lua UTF-8 直接作为 Modified UTF-8 传入。

启动配置、资源清单及资源文件由 App 从自身 APK 读取、校验并导出至 `context.getFilesDir()/offline-bootstrap`。小体积入口配置另写入 `context.getExternalFilesDir(null)/offline-bootstrap/1.0.1/config.txt`，其正文仍指向当前用户的内部资源目录，不复制整套资源至外部目录。打包时将 metadata 配置入口固定为 `file:///sdcard/Android/data/<实际包名>/files/offline-bootstrap`；正式包使用 `com.ymfy.shxjl2mdb.aiqu`，独立验收包须同时替换 metadata 中的包名。入口字面量追加至 metadata 文件尾并更新字面量索引及数据区长度，其他表偏移不移动。`UnityMetadataCache` 校验入口对应当前包名，再与 APK 原样同步缓存，保持缓存与 APK 的长度和字节一致。

此方式依据独立验收包实际取证调整：先前仅在启动前写入更长的动态 metadata 缓存时，Unity 将其覆盖为 APK 内的原长占位入口，导致一直停在配置加载 0%。现改为 APK 本身携带正确入口，即使 Unity 重新提取缓存也不退回占位符。ARMv7 原 `LoadConfig` 会拼接 `/1.0.1/config.txt?r=<时间戳>`，导出目录与路径一致；是否需要进一步处理文件 URI 查询参数仍以设备回归为准，当前不声称已通过。

`login_model` 的区服和角色历史读取、`sdk_mgr.order` 的创建订单动作通过同一 App 桥直接执行，不使用原 `WWW` 或 `SDKAdapter.Order` 的 HTTP 路径。参数与结果继续使用原客户端格式，资源增量同步两级清单与摘要。

消息生命周期按角色会话代次隔离：新建会话先清空旧帧；连接通知在下一帧交给原回调；请求生成的帧排入待分派队列，保留原会话登记先于应答分派的顺序。处理帧期间若回调导致断开或重新连接，旧代次剩余帧立即停止分派。`Network.Destroy` 捕获并关闭本模块自身的 proxy，停止旧轮询并清除暂存帧，不借助全局变量关闭其他模块的新会话。App 定时业务与读取推送均应遵循共享 SQLite 提交边界，失败操作不得泄露未提交的帧。

模拟充值在用户已有商品购买动作后直接进行本地报价与确认，移除 Android 二次确认弹窗；不产生真实付款。Unity 先经 App 创建订单，再沿原 `purchase` 回调完成结算。同一订单仍须由业务唯一键保证只记账、发奖一次，移除弹窗不改变幂等要求。游戏暂停期间的已提交推送由 App 队列保留，Unity 恢复后轮询取回。

当前静态检查已核对双 ABI 原网络、选服和订单入口；Lua 源码 mock 已验证连接、请求、轮询、分派、断开、历史参数转义和订单续接，JNI 双 ABI 已编译并核对 ELF 架构、16KB 段对齐及无外部动态库依赖。上述结果不等于原双 ABI 字节码的设备运行通过。生效须完成本次 App 构建及安装，设备回归仍待执行：断网且无 ADB 转发时冷启动、登录与建角；无 HTTP/TCP 监听；单次购买无第二弹窗且即时到账；同单重复确认不重发资产；主城、强化、洗炼与战斗；退出、重连及重启存档；切换角色不收到旧代次帧。

### 2026-11-21 · v4 到账推送的共享事务修正（历史方案）

适用范围为已登录角色在模拟订单结算后五秒内的盲盒 S464、充值 S11 及关联资产推送。来源为 v4 交付源码与本地验收：`LocalGameGateway` 新增的 `pump` 曾直接运行，未进入既有 `sendCommitted → EmbeddedStore.write` 路径，而充值推送包含订单通知状态写入。

本次修正由 `GameGatewayService.needsPump` 在事务外检查内存中的角色就绪状态和结算窗口，窗口外的 250ms 轮询不创建 SQLite 事务。窗口内统一通过 `sendCommitted` 执行 `pump`，因此通知状态查询与更新使用 APK 已注册的共享数据库事务，帧缓冲在提交成功后发送；事务抛出异常时清理缓冲并丢弃该次暂存帧。实际网络送达仍不等于客户端确认，本次不变更既有订单通知重试语义。

生效条件为使用本次源码重新构建并安装 APK；旧 v4 APK 不会因源码修改而自动生效。当前完成路径与差异静态核对，编译结果由本次服务端版本记录统一登记，尚未完成设备回归。设备回归需覆盖：支付确认后不操作且五秒内收到盲盒与充值更新；相同订单重复确认不重发资产；退出及重新登录可读取已提交存档；注入提交失败时不发送本次暂存帧，并确认窗口外不进入共享事务。
